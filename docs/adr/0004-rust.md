# ADR-0004 · Rust como plataforma de ejecución del servicio

- **Fecha:** 2026-11-07.
- **Estado:** implementada; integración sujeta a los controles del PR.
- **Alcance:** servicio HTTP, casos de uso, adaptador de persistencia, pruebas y herramientas de verificación.

## Contexto y restricciones

La plataforma de ingesta y análisis requiere confirmación transaccional, deduplicación concurrente, autorización por rol y fuente, contratos HTTP verificables y recuperación ante fallos de PostgreSQL. La implementación debe distribuirse como una unidad operativa, con dependencias reproducibles y separación explícita entre transporte, aplicación y persistencia.

PostgreSQL continúa siendo la autoridad de consistencia y el motor de agregaciones. El lenguaje de aplicación no modifica sus garantías ACID ni elimina los límites de disco, red o capacidad de consulta.

## Decisión

Se establece una implementación **íntegramente en Rust**, sin intérprete ni componentes de aplicación Python:

| Responsabilidad | Tecnología / contrato |
|---|---|
| HTTP y concurrencia | Axum sobre Tokio; I/O asíncrono y apagado por SIGINT/SIGTERM |
| Contratos y validación | Serde, Chrono, enums y validación de dominio explícita |
| Persistencia | SQLx, consultas parametrizadas y transacciones PostgreSQL |
| Esquema | Migraciones SQL versionadas y embebidas; ejecución operativa explícita |
| API | OpenAPI generado con Utoipa a partir de rutas y tipos |
| Calidad | Rust/Cargo fijados, Cargo.lock, rustfmt, Clippy, pruebas y rustdoc |
| Distribución | Binario release en imagen multi-stage con usuario no privilegiado |

Se conserva el monolito modular. `EventService` depende del puerto `EventRepository`; `PostgresRepository` implementa el adaptador real. La composición de dependencias se realiza en `main.rs`, sin estado de negocio global mutable ni contenedor de inyección.

## Justificación y alternativas

- **Stack Rust único:** unifica compilación, comprobación estática, pruebas y herramientas operativas bajo Cargo; evita administrar dos runtimes de aplicación.
- **I/O asíncrono:** permite atender solicitudes concurrentes sin bloquear hilos durante consultas o backoff. La concurrencia hacia PostgreSQL sigue acotada por el pool.
- **Monolito frente a microservicios:** mantiene una única unidad de entrega y evita contratos distribuidos y componentes que el escenario no requiere.
- **SQL explícito frente a ORM:** hace visibles los límites transaccionales y las consultas analíticas; su corrección se verifica contra PostgreSQL real.
- **Sin implementación híbrida:** no se introducen bindings, procesos auxiliares ni duplicación permanente de casos de uso entre lenguajes.

## Consecuencias

La compilación y el mantenimiento requieren experiencia con Rust, ownership y programación asíncrona. La tipificación y el binario compilado son propiedades de la implementación; cualquier afirmación sobre latencia, throughput, RSS o ahorro económico requiere un benchmark comparativo reproducible. Esta decisión no acredita por sí sola mejoras de rendimiento ni el presupuesto cloud.

Los eventos mantienen su esquema relacional y contrato HTTP. Las escrituras confirman solo después de COMMIT; no se reintentan automáticamente. El listado y resumen mantienen coherencia entre sus sentencias mediante un snapshot repetible.

## Compatibilidad y operación

- DSN admitido: `postgresql://` o `postgres://`; convertir DSNs específicos de drivers anteriores antes del despliegue.
- La configuración se lee al inicio; la rotación de credenciales requiere reemplazar los procesos.
- SQLx registra versiones en `_sqlx_migrations`. La tabla histórica `alembic_version`, si existe, se conserva sin utilizarla como autoridad nueva.
- La adopción de una tabla existente valida estructura y restricciones antes de registrar la migración. Requiere backup y ensayo previo sobre una copia.
- `serve` no modifica el esquema. Ejecutar `event-service migrate` como paso controlado anterior al despliegue.
- Límites de entrada: cuerpo HTTP de 4 MiB, payload de 16 KiB por evento y lote de 1–100 eventos.

## Criterios de verificación

1. Formato, Clippy sin advertencias, pruebas y rustdoc aprobados.
2. Aceptación contra PostgreSQL: concurrencia, atomicidad, ventanas UTC y agregaciones.
3. Adopción del esquema existente sin reescritura de eventos y rechazo de estructuras incompatibles.
4. Recuperación `200 → 503 → 200` sin reiniciar la API y durabilidad tras reiniciar componentes.
5. OpenAPI exportable sin DB e imagen ejecutable como usuario no root.

La evidencia local y la evidencia CI se registran por separado. Azure/K3s, publicación de imágenes, HA y objetivos de servicio requieren sus verificaciones de despliegue correspondientes.
